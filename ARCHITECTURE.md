# ARCHITECTURE.md — NextOne Flutter App

> **Source of truth for the post-refactor architecture.**
> All implementation subtasks (ST-001 through ST-008) must conform to the structures, rules, and conventions defined here.

---

## 1. Purpose

This document defines the target architecture for the NextOne Flutter mobile application after the `refactor-001` effort completes.

The refactor achieves three goals:

1. **Consolidate the monorepo packages** (`packages/nextone_core` and `packages/models`) into a single `lib/` source tree, eliminating cross-package import friction and simplifying the build graph.
2. **Remove `flutter_hooks` / `HookWidget`** in favour of standard Flutter `StatefulWidget` lifecycle management (`initState`, `dispose`).
3. **Remove `auto_mappr` / `auto_mappr_annotation`** in favour of plain Dart `factory` constructors and extension methods.

The resulting app uses a centralised layered architecture inside lib/, guided by Clean Architecture principles.

## 3. Layer Dependency Rules

The layers form a strict directed acyclic graph. A layer may only import from layers listed under "may depend on".

```
┌─────────────────────────────────────────────────────────┐
│                     presentation/                        │
│  (pages, widgets, BlocBuilder, BlocListener)            │
└───────────────────────┬─────────────────────────────────┘
                        │ depends on
                        ▼
┌─────────────────────────────────────────────────────────┐
│                     application/                         │
│  (BLoC, events, states — orchestrates domain + data)    │
└──────────────┬──────────────────┬──────────────────────┘
               │                  │
               ▼                  ▼
┌──────────────────┐   ┌──────────────────────────────────┐
│     domain/      │   │            data/                  │
│  (entities,      │   │  (models, DTOs, mappers,          │
│   repo interfaces│   │   repo/service interfaces +       │
│   if pure Dart)  │   │   Supabase implementations)       │
└──────────────────┘   └──────────────────────────────────┘
               │                  │
               └────────┬─────────┘
                        │ both depend on
                        ▼
┌─────────────────────────────────────────────────────────┐
│                       core/                              │
│  (injection, constants, supabase config, BlocObserver)  │
└─────────────────────────────────────────────────────────┘
```

**Concrete rules:**

| Layer | May depend on | Must NOT depend on |
|---|---|---|
| `presentation/` | `application/`, `domain/`, `data/models`, `core/`, `shared/` | Nothing above it |
| `application/` | `domain/`, `data/interfaces`, `core/` | `presentation/` |
| `domain/` | `core/` (constants only) | `application/`, `data/`, `presentation/` |
| `data/` | `domain/entities`, `core/` | `application/`, `presentation/` |
| `core/` | Dart SDK, Flutter SDK, third-party packages | All app layers |
| `shared/widgets/` | Flutter SDK, `core/`, `domain/entities` | `application/`, `data/` |

**Repository and service interface placement:**
- Interfaces (`IAuthService`, `IArtistRepository`, etc.) live in `data/repositories/interfaces/` and `data/services/interfaces/`.
- Implementations live in `data/repositories/implementations/` and `data/services/implementations/`.
- The `domain/repositories/` directory is reserved for interfaces that are pure domain contracts with no data-layer types in their signatures. In practice, most interfaces live in `data/` for this project.

## 5. Widget Classification Rules

### Page widgets (`presentation/<feature>/<feature>_page.dart`)

- Registered as a named route in `app_router.dart`.
- Must be `StatelessWidget` or `StatefulWidget`. **`HookWidget` is prohibited.**
- Access BLoC state via `BlocBuilder` or `BlocConsumer`. Never via `context.watch<Bloc>()` outside a build method.
- Dispatch BLoC events via `context.read<Bloc>().add(event)`.
- Own no business logic. All state transitions go through BLoC events.

### Feature-scoped widgets (`presentation/<feature>/widgets/`)

- Sub-widgets used only within one feature.
- Same StatefulWidget / StatelessWidget rules as pages.
- Must not import from sibling features' `presentation/` directories.

### Shared widgets (`presentation/shared/widgets/` → long-term `shared/widgets/`)

- Reusable across two or more features.
- Must be self-contained: no feature-specific BLoC dependencies.
- May accept callbacks and configuration via constructor parameters.
- If the widget manages local ephemeral state (e.g., `nextone_text_field.dart` managing its own error text and controller), it must be a `StatefulWidget` with proper `initState` / `dispose`.
- The optional `TextEditingController` pattern: accept an external controller as a nullable constructor parameter; if `null`, create an internal one in `initState` and dispose it in `dispose`.

### StatefulWidget lifecycle rules

These rules apply wherever `HookWidget` has been replaced:

```dart
class _MyPageState extends State<MyPage> {
  late final TextEditingController _ctrl;
  // Late-initialise in initState, not at declaration, to avoid
  // accessing widget before the State is mounted.

  @override
  void initState() {
    super.initState();
    _ctrl = TextEditingController();
    _ctrl.addListener(_onTextChanged); // add listeners here
  }

  @override
  void dispose() {
    _ctrl.removeListener(_onTextChanged); // remove before dispose
    _ctrl.dispose();
    super.dispose();
  }
}
```

- Every `TextEditingController` created inside `State` must be disposed in `dispose()`.
- Every `Timer` created inside `State` (e.g., `loading_splash_page.dart`) must be cancelled in `dispose()`.
- `setState()` must never be called after `dispose()`. Cancel timers and remove listeners to prevent this.

## 7. Refactor Phases Summary

The refactor is executed in 8 subtasks with explicit ordering enforced by the dependency graph.

```
ST-001 ──► ST-002 ──► ST-005 ──► ST-007
       │                    │
       └──► ST-003 ──► ST-004   └──► ST-008
                 │
                 └──► ST-006
```

| ID | Title | Type | Priority | Depends on | Parallelisable with |
|---|---|---|---|---|---|
| ST-001 | Consolidate packages into `lib/` | architecture | 1 | — | — |
| ST-002 | Replace `auto_mappr` with manual mappers | architecture | 2 | ST-001 | ST-003 |
| ST-003 | Convert `HookWidget` pages to `StatefulWidget` | ui | 3 | ST-001 | ST-002 |
| ST-004 | Remove `flutter_hooks` from `pubspec.yaml` | dependency | 4 | ST-003 | — |
| ST-005 | Update injection config + re-run `build_runner` | architecture | 5 | ST-001, ST-002 | ST-006 |

| ST-007 | Write unit tests for BLoC layer | tests | 7 | ST-001, ST-002, ST-005 | — |
| ST-008 | Final cleanup and validation | quality | 8 | ST-001 – ST-007 | — |

### Phase descriptions

**ST-001 — Consolidate packages into `lib/`**
Copy all Dart source from `packages/models/lib/src/` and `packages/nextone_core/lib/src/` into the target paths in `lib/` (see migration table above). Update `pubspec.yaml` to remove the `nextone_core` and `models` path dependencies and absorb their transitive dependencies directly. Run a global import replacement (`package:nextone_core/` → `package:nextone/`, `package:models/` → `package:nextone/`). Delete the `packages/` directory.

**ST-002 — Replace `auto_mappr` with manual mappers**
Read each `*.auto_mappr.dart` generated file to understand field mappings before deleting them. Write `fromApiResponse()` factory constructors on each DTO class. Remove `auto_mappr` and `auto_mappr_annotation` from all `pubspec.yaml` files. Delete all `*.auto_mappr.dart` files.

**ST-003 — Convert `HookWidget` to `StatefulWidget`**
Apply the `StatefulWidget` template to each of the 8 files listed in the migration table. Dispose all `TextEditingController` and `Timer` instances in `dispose()`. Replace `BlocBuilder` where `context.watch` was used inside a `HookWidget` build method.
